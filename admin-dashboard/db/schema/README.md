# Baseline schema

A capture of the live Postgres schema, in version control.

The schema itself is still managed in the Supabase dashboard — these files are
**not** its source of truth, and applying them to the live project is not the
intended use. They exist so schema change is reviewable in diffs, so a scratch
or test database can be built from something, and so the shape of the data model
can be read without dashboard access.

Captured from project `pfcncajijvtvsdwgwbjl` ("EBTL 1", eu-west-1, Postgres 17).

## What is here

| File | Contents | Status |
| --- | --- | --- |
| `00_extensions_and_types.sql` | 4 extensions, 11 enum types | captured |
| `10_tables.sql` | 53 tables — columns, defaults, generated/identity columns, RLS enablement | captured |
| `20_constraints.sql` | 261 constraints — 53 PK, 30 unique, 87 check, 91 FK | captured |
| `30_indexes.sql` | 168 indexes (excluding constraint-backed ones) | **not captured** |
| `40_views.sql` | 8 views | **not captured** |
| `50_functions.sql` | 13 functions | **not captured** |
| `60_triggers.sql` | 34 triggers | **not captured** |
| `70_rls_policies.sql` | 86 RLS policies | **not captured** |
| `80_comments.sql` | table and column comments | **not captured** |

Counts come from the catalogs and match the captured files exactly where a file
exists. The missing files are regenerated by `../tools/dump_schema.sql`, which
contains the query for every section including the ones already captured — run
the section, write its single `ddl` column to the matching filename.

## What this capture does not prove

**Nothing here has been applied to a database.** The files were produced by
reading system catalogs; no DDL was executed against the live project, and none
should be. That also means the baseline is **unverified**: nobody has confirmed
that running these files against an empty database reproduces the schema.

Verifying it needs a scratch Postgres 17 — a container, or a Supabase branch
(which is a paid resource). Until that has been done, treat the files as an
accurate transcription rather than a tested bootstrap.

## Ordering

Filename order is apply order: types before tables, tables before the
constraints that reference them, and primary/unique keys before the foreign keys
that point at them. Views and triggers depend on functions, so `50` precedes
both.

## RLS

Row-level security is enabled on all 53 tables and there are 86 policies. The
Express server connects with the service-role key
(`server/lib/supabase.js`), which **bypasses RLS entirely** — so today those
policies govern only direct PostgREST access, and every authorization decision
the customer and admin APIs make is in application code. That is worth knowing
before assuming the policies protect anything the server does.
